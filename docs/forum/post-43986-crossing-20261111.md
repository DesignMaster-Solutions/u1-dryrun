Update, 11 November: a whole print-farm plate, and a new kind of finding. Both come from the file Mr.Borispol shared after Snapmaker Orca 2.4.1 damaged prints on his five U1s (27 bunnies, 22 h 38 min, 8.8 million lines, 186 tool changes: https://forum.snapmaker.com/t/43745/12).

**Large plates now run whole.** That file was killed for memory in a default 8 GB Docker. Now it finishes there in about 7 minutes. A run cut by the time limit now says NOT FINISHED instead of clean, which was wrong.

**New finding in the report: CROSSING.** In 52 of the 186 tool changes on that plate, the slicer lowers the new head to layer height while it is still at its dock, then sends it straight to the prime tower through what the current layer has just printed, 5.0 to 40.5 mm each time, from Z0.45 up to Z42.85. Later layers cover the marks, so the scar check alone called this file clean. The report now lists each one as `CROSSING line N` and exits 1. The cause in the slicer source and the list of lines are in https://github.com/Snapmaker/OrcaSlicer/issues/1168, with no reply from Snapmaker yet.

What it does not prove: I have not matched those lines to the damage in his photos, and I have not sliced the same plate on 2.4.0. Files without a prime tower are not checked for this.

Release v1.1.0 has both: https://github.com/DesignMaster-Solutions/u1-dryrun/releases/tag/v1.1.0

That makes real files from four U1 owners so far. If you have a multicolor print that came out marked or failed mid-way, I would like to run it.
