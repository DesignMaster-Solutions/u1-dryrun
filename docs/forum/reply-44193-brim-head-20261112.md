I could reproduce this in the sliced file, without a printer, and it is not limited to "by object".

Three 15 mm blocks, one filament each, outer brim, Snapmaker Orca 2.4.1 (macOS command line). The file has a single brim block: all three brims are printed with T0 before any object starts. With "by object", block b (T1) only starts after block a is finished and block c (T2) after a and b, which is the cooling you describe. With "by layer" the brims are still all printed by T0, so the wrong colour is there too. The same three blocks in OrcaSlicer 2.5.0-rc give one brim per object, printed by that object's head right before it, as KCC_703 saw.

Until the fix ships, this small Python script (no dependencies) reads a sliced file and says which objects get their brim from another head: https://github.com/DesignMaster-Solutions/u1-dryrun/blob/main/tools/brim_wrong_head.py

```
$ python3 brim_wrong_head.py brim-by-object-orca-2.4.1.gcode.gz
BRIM ON ANOTHER HEAD: 2 object(s)
  b.stl: printed by T1, its brim by T0 (line 629); 1 other object(s) are printed in full before this one starts
  c.stl: printed by T2, its brim by T0 (line 1074); 2 other object(s) are printed in full before this one starts
```

Both sliced files are in the repository's `examples/` folder, so anyone can repeat it.

Limits: these are my own test blocks, not your plate, and I have not printed them. The script matches each brim to the nearest object, so parts nested inside each other can be matched wrongly. I did not test a workaround in 2.4.1.
